    project

    overview

    Caracal answers nearest-neighbour queries between two parties that don't trust each other. The server holds the vectors and never sees a query or its results. The client gets back the ids of its k nearest vectors and nothing else: no stored vectors, no distances.

    Underneath it is an ordinary IVF index. K-means splits the vectors into lists, and a search scores every list centroid, opens the nearest few lists and ranks the vectors inside them. Caracal runs each of those steps under homomorphic encryption, private information retrieval or a garbled circuit, so neither side sees the other's half. The ranking inside the opened lists is exact, so a private search returns the same ids as a plaintext search over the same lists.

    It runs as two processes. The server holds named indexes and takes ingests over a REST admin API. The client serves a search REST API and runs each search against the server over streaming RPC.

    how a search runs

    1. 01 / score lists

      The client quantizes its query and encrypts it with BFV (Microsoft SEAL). The server computes the distance to every list centroid on the ciphertext and splits each result into two additive shares: it keeps one, and the client decrypts the other. Either share alone is random noise.

    2. 02 / pick lists

      The two sides feed their shares into a secure top-k, run as a garbled circuit (EMP-toolkit). Only the client learns which nprobe lists came out nearest, and the labels it learns are reshuffled for every query.

    3. 03 / fetch lists

      The lists are packed into nprobe buckets, and the client sends one PIR query to every bucket, padding where it has nothing to ask. Each answer touches the whole bucket, so the server can't tell which list, if any, it returned. Lists that sit near each other are coloured into different buckets, so the nearest few rarely share one. When two do, only one of them is fetched.

    4. 04 / rank vectors

      The fetched lists arrive split into shares between the two sides. Together they compute each vector's distance to the query, run an exact secure top-k, and reveal the k nearest ids to the client. Padding entries are dropped from the result.

    who learns what

    server learns that a search ran, and its settings (nprobe, k)
    server never sees the query, which lists it opened, any distance, the result
    client learns its k nearest ids, and per-query labels for the lists it opened
    client never sees stored vectors, centroids or distances
